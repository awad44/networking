Slide 6

IntServ vs DiffServ

EXPLAINED

IntServ treats every flow individually and requires signalling before data is sent. DiffServ takes the opposite approach: it defines a small number of traffic classes, and every packet carries its class in the header. Routers treat all packets of the same class the same way, regardless of which flow they belong to.
There is no signalling and no per-flow state in the core, so DiffServ scales to any network size. The price is that guarantees are relative and statistical rather than absolute: EF traffic gets better service than best effort, but there is no per-flow mathematical bound unless the network is carefully provisioned.
An airline analogy fits well: IntServ is booking a specific seat on every flight leg; DiffServ is buying a business-class ticket — you are treated better than economy, but your exact experience depends on how full business class is.

EXAMPLE

A provider with 2 million VoIP calls needs only one EF queue on each core router, not 2 million reservations.

REMEMBER

DiffServ = per-class treatment, no signalling, scales to the Internet core; guarantees depend on provisioning.

Slide 8

Edge vs core responsibilities

EXPLAINED

DiffServ deliberately places all the complex work at the edge of a domain. Boundary routers classify incoming traffic, measure it against the traffic contract, mark it with the correct DSCP and police or shape it if it exceeds the agreed profile.
Interior routers do almost nothing extra: they read the DSCP, place the packet in the corresponding queue and apply the drop policy. This behaviour is called a Per-Hop Behaviour (PHB).
A DS domain is a set of routers sharing the same class definitions — typically one organisation or provider. Between domains, a Service Level Agreement and its technical part, the Traffic Conditioning Agreement, define which classes are accepted, at what rates, and how markings are translated at the border.

EXAMPLE

An enterprise marks voice as EF. Its provider uses DSCP 40 for voice internally, so the provider edge re-marks EF ⇒ 40 on ingress and back on egress.

REMEMBER

Smart edges (classify, meter, mark, police) + simple core (PHB per DSCP) = scalability.

Slide 10

The DS field (RFC 2474 / 3168)

EXPLAINED

DiffServ reuses the old Type of Service byte in the IPv4 header (and the Traffic Class byte in IPv6). The first six bits are the DSCP (Differentiated Services Code Point), giving 64 possible values. The last two bits are used by ECN.
Before DiffServ, the first three bits were called IP Precedence. To remain compatible, DSCP values whose last three bits are zero (xxx000) are the Class Selector code points CS0–CS7, which behave like precedence 0–7.
Students often confuse the DSCP value with the ToS byte value. Because the DSCP occupies the upper six bits, the ToS byte equals DSCP × 4 (shifted left by 2 bits). Tools like tcpdump print the ToS byte, while Wireshark shows both.

EXAMPLE

EF = DSCP 46 = binary 101110. Shifted left by two bits: 10111000 = 0xB8 = 184. So ping -Q 0xb8 sends packets marked EF.

REMEMBER

ToS byte = DSCP × 4 + ECN. DSCP 46 (EF) ⇔ ToS 0xB8.

Slide 12

The standard PHBs

EF

EF — Expedited Forwarding

DSCP 46 (RFC 3246). Low delay, low jitter, low loss. Served by a priority queue and policed at the edge. For voice.

AF

AF — Assured Forwarding

4 classes × 3 drop precedences (RFC 2597). Each class gets bandwidth; under congestion higher drop precedence is dropped first.

CS

CS — Class Selector

CS0–CS7, backward compatible with IP Precedence. CS6 for network control (routing), CS3/CS4 often signalling.

BE

Default / BE

DSCP 0. Best effort. Should receive a reasonable bandwidth share (often ≥ 25%). LE (DSCP 1, RFC 8622) for scavenger traffic.

12

Slide 13

The standard PHBs

EXPLAINED

Expedited Forwarding (EF) is designed for traffic that needs low delay, low jitter and low loss — classically voice. Routers serve EF from a priority queue. Because priority queues can starve other traffic, EF must be policed at the edge so its volume stays small.
Assured Forwarding (AF) defines four independent classes, each with its own queue and bandwidth share, and three drop precedences within each class. When an AF queue becomes congested, packets with high drop precedence are dropped first. This is ideal for business data that should be protected but can tolerate some delay.
Class Selector (CS) values keep compatibility with IP Precedence; CS6 is commonly used for routing protocol traffic. Default (DF, DSCP 0) is best effort, and the newer Lower Effort (LE, DSCP 1) marks scavenger traffic that should use only otherwise idle capacity.

EXAMPLE

Voice bearer → EF; video conferencing → AF41; ERP → AF21; backups → AF11; OSPF/BGP → CS6; software updates → LE.

REMEMBER

EF = priority (policed). AF = 4 classes × 3 drop levels. CS = legacy/control. DF = best effort. LE = scavenger.

14

Slide 15

Assured Forwarding code points

EXPLAINED

AF code points are written AFxy, where x (1–4) is the class and y (1–3) is the drop precedence. The class decides which queue the packet uses and therefore its bandwidth share. The drop precedence decides how early the packet is dropped inside that queue under congestion.
The decimal DSCP is DSCP = 8x + 2y. Classes do not imply priority over each other: AF4 is not automatically better than AF1 — the network operator decides how much bandwidth each AF class receives.
Drop precedence is usually set by a three-colour policer at the edge: traffic within the contract is marked AFx1 (green), moderate excess AFx2 (yellow) and large excess AFx3 (red). WRED then uses different thresholds for each, so out-of-contract traffic is discarded first.

EXAMPLE

AF32 = 8×3 + 2×2 = 28. A customer exceeding its committed rate sees its extra traffic re-marked from AF31 (26) to AF32 (28) and dropped first when AF3 is congested.

REMEMBER

AFxy: x = queue/class, y = drop precedence. DSCP = 8x + 2y.

Slide 17

Common class mapping (RFC 4594-style)

EXPLAINED

RFC 4594 gives operators a recommended mapping from service types to DSCPs. Using standard values makes it easier to interconnect equipment from different vendors and to exchange traffic between organisations.
Each class is matched to a treatment: network control (routing protocols) gets guaranteed bandwidth because if routing fails, everything fails; telephony gets a policed priority queue; signalling and video get bandwidth guarantees; data classes get bandwidth plus WRED; best effort gets the default queue; scavenger traffic gets whatever is left.
Real devices usually have only 4–8 hardware queues, so several classes are combined. The table is a starting point; each organisation adapts it to its applications and hardware.

EXAMPLE

A 4-queue model: Queue 1 (priority) = EF; Queue 2 = CS6 + CS3 + AF4x; Queue 3 = AF2x + AF3x; Queue 4 = AF1x + DF + LE.

REMEMBER

Use standard DSCPs, then map them onto the queues your hardware actually has.

19

Slide 20

Traffic conditioner at the DS boundary

EXPLAINED

A traffic conditioner is the chain of functions applied when traffic enters a DS domain. The classifier selects packets — either by existing DSCP (behaviour-aggregate classification) or by multiple header fields such as addresses and ports (multi-field classification).
The meter compares the classified traffic with its profile, usually a token bucket as in Lecture 4, and reports whether each packet is in or out of profile. The marker sets or changes the DSCP accordingly.
Finally, the shaper/dropper enforces the profile: for EF, excess packets are dropped so the priority queue is never overloaded; for AF, excess packets are typically re-marked rather than dropped. The conditioner is where the SLA is technically enforced.

EXAMPLE

A provider’s edge: classify customer VoIP (EF), meter at 5 Mb/s, drop anything above 5 Mb/s; classify other traffic as AF21, meter with trTCM, re-mark excess to AF22/AF23.

REMEMBER

Classify → meter → mark → shape/drop. This is where contracts become packet treatment.

Slide 22

DiffServ over MPLS (RFC 3270)

EXPLAINED

In MPLS networks, core routers forward on labels and do not look at the IP header, so they cannot read the DSCP. The class must therefore be represented in the MPLS label stack.
With E-LSPs (EXP-inferred LSPs), the 3-bit Traffic Class field of each label carries the class, so up to 8 behaviours share one LSP. The ingress PE maps DSCP to TC. This is the common approach. With L-LSPs (label-inferred), a separate LSP is built for each class, and the label itself tells the router which queue to use; TC carries only drop precedence. L-LSPs combine naturally with RSVP-TE to give each class its own engineered path.
RFC 3270 also defines tunnelling modes: in uniform mode the provider’s marking overwrites the customer’s; in pipe and short-pipe modes the customer’s original DSCP is preserved and restored at the egress, so providers can apply their own policy without disturbing the customer’s markings.

EXAMPLE

Customer DSCP EF ⇒ ingress PE sets MPLS TC = 5 ⇒ core routers queue TC 5 in the priority queue ⇒ egress PE pops the label; with pipe mode the customer still sees DSCP 46.

REMEMBER

MPLS carries the class in the TC bits (E-LSP) or in the label (L-LSP). Tunnelling modes decide whether customer DSCP is preserved.

Slide 23

End-to-end QoS design guidelines

1

Keep it simple

Start with 4–6 classes; add classes only when a real application needs them.

2

Limit priority traffic

Keep EF/priority ≤ ~33% of link capacity to preserve headroom for other classes.

3

Protect control traffic

Reserve bandwidth for routing and management (CS6/CS2) so the network stays manageable under load.

4

Trust boundary

Trust markings only from known devices (IP phones, servers); re-mark everything else at access.

5

Consistency

Apply the same policy on every congestion point: WAN edges, uplinks, wireless.

6

Verify

Monitor per-class drops and delay; validate with synthetic tests (IP SLA, TWAMP).

Slide 24

End-to-end QoS design guidelines

EXPLAINED

Good QoS designs are simple: start with four to six classes and add more only when a real application requires it. Each additional class costs configuration, testing and troubleshooting effort.
Limit priority traffic to about a third of a link, because priority queues are served first and could starve everything else. Always reserve bandwidth for network control traffic so routing and management keep working during congestion. Define a clear trust boundary and re-mark untrusted traffic.
Apply the policy consistently at every congestion point — WAN edges, data-centre uplinks, Wi-Fi — because one unprotected bottleneck ruins the end-to-end result. Finally, verify: monitor per-class drops and delay, and use synthetic probes (IP SLA, TWAMP) to prove the SLA is met. Remember that most public Internet providers reset DSCP to 0, so DiffServ normally works within a domain or under a contract.

EXAMPLE

A 50 Mb/s branch link: EF 10% (priority, policed), AF41 25%, AF21 25%, AF11 10% with WRED, CS6 5%, default 25%.

REMEMBER

Few classes, capped priority, protected control traffic, trust boundary, consistent policy, continuous verification.

Slide 27

Model answers

A1

Core routers keep no per-flow state: they only look at the 6-bit DSCP and apply a fixed set of class behaviours. Per-flow work (classification, metering, policing) happens only at the edge.

A2

AF23 = 8×2 + 2×3 = 22. EF = 46 ⇒ ToS byte = 46 × 4 = 184 = 0xB8 (with ECN bits 00).

A3

EF uses a priority queue that is always served first; without a policer, excess EF traffic could consume the whole link and starve all other classes.

A4

Both use the AF1 queue, but AF13 has the higher drop precedence, so WRED starts dropping AF13 at a lower queue depth; AF11 packets survive longer.

Key takeaways

DiffServ classifies at the edge and applies per-class PHBs in the core — no per-flow state

The 6-bit DSCP selects the PHB; the remaining 2 bits carry ECN

EF = low-latency priority (policed); AF = 4 classes × 3 drop precedences; CS = legacy precedence

Edge conditioners meter, mark, shape and drop according to the TCA

Good designs use few classes, cap priority traffic and enforce a trust boundary
